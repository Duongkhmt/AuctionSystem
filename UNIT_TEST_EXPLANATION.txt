1. BẢN CHẤT CỦA UNIT TEST VÀ NGUYÊN TẮC CÔ LẬP (ISOLATION PRINCIPLE)
================================================================================

1.1. Phân biệt Unit Test (Kiểm thử đơn vị) và Integration Test (Kiểm thử tích hợp):
----------------------------------------------------------------------------------
- Integration Test (`@SpringBootTest`): 
  + Khởi chạy toàn bộ Spring IoC Container, khởi tạo tất cả các Bean (`@Component`, 
    `@Service`, `@Repository`), thiết lập kết nối Database PostgreSQL thật/H2, 
    Security Filter Chain và Hibernate/JPA.
  + Nhược điểm: Tốc độ rất chậm (mất từ 10 - 30 giây để boot Spring). Nếu hệ thống 
    có hàng trăm bài test, thời gian chạy sẽ lên tới hàng chục phút.
- Pure Unit Test (Kiểm thử đơn vị thuần túy):
  + KHÔNG bật Spring Container, KHÔNG kết nối Database thật, KHÔNG bật Web Server.
  + Tất cả các bài test chạy trực tiếp trên bộ nhớ RAM của JVM thông qua Java Reflection 
    và Bytecode Dynamic Proxy.
  + Ưu điểm: Tốc độ thực thi siêu tốc (toàn bộ **53 test cases** của dự án chạy chưa tới **1.5 giây**).

1.2. Nguyên tắc cô lập (Isolation Principle):
----------------------------------------------
- Khi kiểm thử một Service (ví dụ `BiddingService`), mục tiêu duy nhất là kiểm tra 
  **logic tính toán và các nhánh điều kiện (if/else) trong chính BiddingService đó**.
- Mọi thành phần phụ thuộc bên ngoài (Repositories, Cloudinary SDK, Mappers, 
  Validators) BẮT BUỘC phải bị vô hiệu hóa và giả lập hoàn toàn (Mocking).
- Lý do cô lập:
  + Giúp bài test không bị thất bại do sự cố mạng, tràn ổ đĩa hay lỗi Database thật.
  + Cho phép lập trình viên kiểm soát 100% dữ liệu đầu vào và giá trị đầu ra của 
    các phương thức phụ thuộc.

2. CƠ CHẾ HOẠT ĐỘNG BÊN DƯỚI JVM CỦA MOCKITO (BYTECODE INTERCEPTION)
================================================================================

2.1. `@Mock` tạo ra đối tượng giả lập như thế nào?
-------------------------------------------------
Khi khai báo `@Mock private ProductRepository productRepository;`:
- Thư viện ByteBuddy (tích hợp trong Mockito) sẽ can thiệp vào ClassLoader lúc Runtime 
  để tạo ra một **Subclass động (Dynamic Proxy Class)** kế thừa từ `ProductRepository`.
- Mockito chèn một bộ can thiệp phương thức (**Method Interceptor**) vào bảng tham chiếu 
  phương thức (v-table) của Proxy Class này.
- Mặc định: Mọi phương thức được gọi trên `@Mock` object sẽ bị Interceptor chặn lại 
  và trả về giá trị mặc định của JVM (`null` cho Object, `0` cho số, `false` cho boolean, 
  `Collections.emptyList()` cho List) mà **KHÔNG CHẠY BẤT KỲ DÒNG CODE THẬT NÀO**.

2.2. Cơ chế Stubbing (`given...willReturn` / `when...thenReturn`):
------------------------------------------------------------------
Khi viết lệnh stubbing:
  `given(userRepository.findById(100L)).willReturn(Optional.of(sampleUser));`
- Mockito ghi nhận thông tin vào một bộ lưu trữ lịch sử gọi (**Invocation Container**):
  *"Nếu phương thức findById được gọi với tham số đầu vào chính xác là 100L, hãy lập tức 
  trả về Optional.of(sampleUser) mà không cần hỏi thêm."*

2.3. `@InjectMocks` làm nhiệm vụ gì?
------------------------------------
Khi khai báo `@InjectMocks private BiddingService biddingService;`:
- Mockito khởi tạo một đối tượng THẬT của `BiddingService`.
- Sau đó dùng **Java Reflection API** duyệt qua constructor và các trường dữ liệu (fields) 
  của `BiddingService`, tự động tiêm tất cả các đối tượng `@Mock` đã tạo ở trên vào.

2.4. Bản chất của `ArgumentCaptor` (Bắt đối tượng lúc Runtime):
---------------------------------------------------------------
Khi test phương thức `executeBuyNow`, đối tượng `Bid` thắng cuộc được khởi tạo mới hoàn toàn 
bên trong `BiddingService`. Ta không thể stub sẵn đối tượng này.
- Cách xử lý:
  `ArgumentCaptor<Bid> bidCaptor = ArgumentCaptor.forClass(Bid.class);`
  `then(bidRepository).should().save(bidCaptor.capture());`
  `Bid capturedBid = bidCaptor.getValue();`
- Bản chất: `ArgumentCaptor` truy cập vào Nhật ký cuộc gọi (Invocation Log) của Mockito 
  để trích xuất chính xác instance `Bid` vừa được truyền vào phương thức `.save()`, giúp 
  ta kiểm tra kỹ từng thuộc tính (`bidAmount`, `isAutoBid`, `bidder`).

3. PHÂN BIỆT TRIỆT ĐỂ: STUBBING VS MOCKING VS SPYING (@Spy)
================================================================================

BẢNG SO SÁNH BẢN CHẤT KỸ THUẬT:

| Khái Nhiệm | Kỹ Thuật | Bản Chất Bên Dưới JVM | Khi Nào Sử Dụng? |
| :--- | :--- | :--- | :--- |
| **Mocking** | `@Mock` | Tạo **Proxy Object giả hoàn toàn**. Mọi method trả về `null/0/false`. Code thật không bao giờ chạy. | Dùng cho Repository, External API, Database kết nối ngoài. |
| **Stubbing** | `given(...).willReturn(...)` | Nạp sẵn dữ liệu phản hồi cho Mock Object khi gặp đúng tham số truyền vào. | Dùng khi muốn ép hàm phụ thuộc trả về dữ liệu mẫu để test nhánh logic. |
| **Spying** | `@Spy` | Bọc xung quanh một **Instance THẬT**. Mặc định 100% code thật của class vẫn chạy bình thường. | Dùng cho Helper/Utility Class khi muốn giữ logic tính toán thật nhưng cần ghi đè 1 phương thức phụ bên trong. |

KỸ THUẬT PARTIAL MOCKING VỚI `@Spy`:
Thực hành trên file `BidStepCalculatorHelperTest.java`:
```java
@Spy
private BidStepCalculatorHelper bidStepCalculatorHelper;

// ⚠️ PHẢI DÙNG CÚ PHÁP doReturn().when(spy)...
doReturn(mockStep).when(bidStepCalculatorHelper).calculateBidStep(eq(currentPrice), any());
```
- TẠI SAO KHÔNG DÙNG `when(spy.calculateBidStep(...)).thenReturn(...)` TRÊN @SPY?
  + Nếu dùng `when(spy.method())`, JVM sẽ **thực thi code thật** của `calculateBidStep` 
    ngay tại dòng stubbing (có thể nảy lỗi Side Effect hoặc NullPointerException).
  + Dùng `doReturn(...).when(spy)` sẽ bảo Mockito chặn Interceptor lại TRƯỚC KHI code 
    thật kịp chạy.

4. CƠ CHẾ ĐO ĐỘ PHỦ CODE CỦA JACOCO (BYTECODE INSTRUMENTATION)
================================================================================

4.1. JaCoCo đo đạc Code Coverage như thế nào?
----------------------------------------------
JaCoCo **KHÔNG** đọc file mã nguồn `.java`. Nó làm việc trực tiếp ở cấp độ **Java Bytecode (`.class`)**:

1. On-the-fly Instrumentation: Khi Maven Surefire khởi chạy test, Java Agent 
   (`-javaagent:jacocoagent.jar`) được đính kèm vào JVM.
2. Tiêm cờ kiểm đếm (Probe Insertion): JaCoCo tiêm các mảng boolean (`boolean[] $jacocoInit`) 
   trực tiếp vào giữa các lệnh bytecode của từng phương thức:
   ```java
   // Code gốc của bạn:
   if (currentPrice < 1000000) { return STEP_LOW; }
   
   // Bytecode sau khi JaCoCo tiêm probe:
   $jacocoInit[0] = true;
   if (currentPrice < 1000000) {
       $jacocoInit[1] = true;
       return STEP_LOW;
   }
   ```
3. Khi bài test chạy xong, JaCoCo tổng hợp kết quả mảng `$jacocoInit`:
   - Instruction Coverage: Tỷ lệ phần trăm opcode bytecode đã chuyển sang `true`.
   - Branch Coverage: Tỷ lệ phần trăm các nhánh quyết định (`ifeq`, `ifne`, `tableswitch`) 
     đã được kiểm tra cả 2 chiều `true` và `false`.
   - Line Coverage: Tỷ lệ các dòng code Java chứa bytecode đã được thực thi.

4.2. Cấu hình Plugin trong `pom.xml`:
------------------------------------
- `prepare-agent`: Khởi tạo Java Agent tiêm probe khi thực hiện lệnh `mvn test`.
- `report`: Tổng hợp file `target/jacoco.exec` ra giao diện trang web HTML tại `target/site/jacoco/index.html`.
- Exclusions: Loại trừ DTO, Entity, Security, Config khỏi báo cáo vì các lớp này chỉ chứa 
  Getter/Setter thuần túy, không có logic rẽ nhánh nghiệp vụ.

5. XỬ LÝ CÁC VẤN ĐỀ ĐẶC THÙ KHI UNIT TEST SERVICE TRONG SPRING BOOT
================================================================================

5.1. Giả lập `TransactionSynchronizationManager`:
------------------------------------------------
- Vấn đề: Phương thức `ProductService.createProduct` có gọi đăng ký sự kiện rollback:
  `TransactionSynchronizationManager.registerSynchronization(...)`.
- Trong Unit Test thuần túy không có Spring Context -> Ném lỗi `IllegalStateException: Transaction synchronization is not active`.
- Giải pháp: Khởi tạo bộ quản lý Transaction giả lập trước mỗi bài test:
  ```java
  @BeforeEach
  void setUp() {
      TransactionSynchronizationManager.initSynchronization();
  }
  @AfterEach
  void tearDown() {
      TransactionSynchronizationManager.clearSynchronization();
  }
  ```

5.2. Cảnh báo Java 21 Dynamic Agent Loading:
--------------------------------------------
- Từ Java 21, JVM in cảnh báo chữ đỏ khi thư viện ByteBuddy tự động gắn Agent lúc Runtime.
- Giải pháp: Bổ sung cờ `-XX:+EnableDynamicAgentLoading` vào thẻ `<argLine>` của `maven-surefire-plugin` trong `pom.xml`.

5.3. Mockito 5 Strict Stubbing (`PotentialStubbingProblem`):
-----------------------------------------------------------
- Mockito 5 áp dụng cơ chế kiểm soát nghiêm ngặt. Nếu bạn khai báo 1 dòng `given(...)` 
  nhưng code trong Service lại không gọi tới (hoặc truyền tham số khác), Mockito sẽ 
  đánh trượt bài test để ngăn chặn việc viết thừa code stubbing không sử dụng.

6. PHƯƠNG PHÁP LUẬN BDD (BDDMOCKITO) VÀ CHU TRÌNH TDD
================================================================================

6.1. BDD (Behavior-Driven Development) với `BDDMockito`:
--------------------------------------------------------
Toàn bộ các bài test trong dự án đều viết chuẩn 3 phần BDD rõ ràng:
- **Given (Giả định bối cảnh)**: Khai báo dữ liệu mẫu và nạp trước phản hồi giả lập (`given(...).willReturn(...)`).
- **When (Hành động)**: Gọi duy nhất phương thức cần kiểm thử.
- **Then (Kỳ vọng & Xác minh)**: Kiểm tra giá trị trả về bằng `assertThat()` và xác minh tương tác bằng `then(mock).should()`.

6.2. Quy trình TDD (Test-Driven Development):
---------------------------------------------
Thực hành trên `AuctionSchedulerTest`:
1. 🔴 **Red Phase**: Viết test case trước cho Robot quét hết giờ -> Chạy lệnh test báo **FAIL**.
2. 🟢 **Green Phase**: Viết mã nguồn xử lý trong `AuctionScheduler` -> Chạy lại test báo **PASS**.
3. 🔵 **Refactor Phase**: Tối ưu mã nguồn cho sạch sẽ mà vẫn giữ bài test ở trạng thái **PASS**.

   - Đặt thầu thành công / thất bại (chặn User/Auction không thấy, chặn cấm đấu giá).

   - Checkout thanh toán chuyển khoản, cập nhật SĐT, địa chỉ giao hàng (`checkout`).
   - Người bán xuất hàng, nhập mã vận đơn (`shipOrder`).
   - Người mua xác nhận đã nhận hàng (`confirmReceived`).

4. `CloudinaryServiceTest.java` (**6 test cases**):
   - Tải lên 1 ảnh đơn lẻ (trả về record UploadedImage chứa URL và public_id).
   - Tải lên danh sách ảnh song song (Parallel Upload).
   - Giả lập đọc byte lỗi IOException ném ngoại lệ RuntimeException.
   - Xóa ảnh trên mây theo public_id hợp lệ / kiểm tra không xóa khi public_id rỗng.

5. `BidStepCalculatorHelperTest.java` (**5 test cases**):

6. `AuctionSchedulerTest.java` (**3 test cases**):
